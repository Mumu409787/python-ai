## 阶段①：LangGraph Checkpointer + Langfuse

**功能：** 已完成的一轮问答写入 LangGraph 的 PostgreSQL 检查点，服务重启后按相同会话编号继续读取。RAG/CHAT 分开，默认保留最近 10 轮、有效期 3600 秒；每次保存刷新有效期，后台清理过期会话。失败或中断的部分回答不保存。并发写入使用数据库锁，同一会话的保存不会互相覆盖；并发生成仍可能基于相同旧历史，建议一轮完成后再追问。

网页验收：

1. 切换“普通聊天”，点“新会话”，发送：`请记住我的验收代号是雪松-638。只需回复已记住。`
2. 回答下方应显示“会话已保存”。按下面的具体命令停止再启动服务，保留当前浏览器页面和会话。
3. 等服务就绪，再发送：`我的验收代号是什么？只回答代号。` 应回答雪松-638。
4. 若刷新网页，之前的聊天正文不会显示，但会话编号保留，服务端历史仍按 TTL 可用。点击“新会话”会换编号；不是删除旧检查点。

**第 2 步具体怎么做：** 当前由后台启动器运行的服务，使用下列命令。先等第一轮回答完成，再保留浏览器当前页面，不刷新、不点“新会话”，也不要切换对话模式。按 Windows 键，搜索并打开 **PowerShell**；在 `PS ...>` 提示符后逐行输入，每行按 Enter：

```powershell
Set-Location 'D:\Projects\python-ai'
.\scripts\stop_demo.ps1
```

第一行进入项目目录；第二行停止本项目网页后端。看到 `Stopped this project application (PID ...)` 表示停止成功。此时暂时不要在网页发问题。在同一个 PowerShell 窗口接着输入：

```powershell
.\scripts\start_demo.ps1
```

看到 `Project is ready: http://127.0.0.1:8000/ ...` 表示重新启动完成。回到刚才保留的网页，在原会话发送第 3 步的问题即可；无需刷新网页。这次只重启网页后端，Docker Desktop 及 PostgreSQL/Qdrant/Redis 保持运行。

若停止命令显示 `has already exited`，记录的服务已经退出，继续启动即可；若显示 `No launcher PID file was found`，它没有找到后台启动记录，不能据此认定服务已停止。若你是自己在终端用 Uvicorn **前台启动**，回到那个持续显示服务日志的终端，按 **Ctrl+C**，等退出日志和 `PS ...>` 提示符出现后，再在项目目录运行 ` .\scripts\start_demo.ps1`。启动时显示 `already running` 说明检测到已有服务，本次没有完成进程重启，应先确认启动方式并真正停止后再验收。

本次已实际更换服务进程并验证代号。模型第一轮可能泛泛说“无法跨会话记忆”，这是模型措辞；本项目通过外部数据库按同一编号提供历史。超过 TTL、换编号或换模式后不会自动沿用。

**旧 Redis 历史不会自动迁移。** 默认 `MEMORY_BACKEND=langgraph`，Redis 后端保留供回退；改回 `redis` 后读取的是另一个后端的历史。不要把 Redis 暂时离线解释为当前 PostgreSQL 记忆丢失。

**调用追踪：** 在网页正常问一次 `42901`，完成后点击答案下方“查看调用链”，进入自己的 Langfuse Cloud 项目。查看根 trace、检索、向量召回、BM25、重排、生成及记忆读写的耗时和状态；有历史时才会出现改写的实际模型调用。上传解析目前不生成独立入库 trace。

默认 `LANGFUSE_CAPTURE_CONTENT=false`：上报长度、模型、来源数量和模型返回的 token 用量等，不上传完整问题、答案、资料。Cloud 上看不到正文属于正常行为；确需查看内容时，在本机 `.env` 改为 true 并重启，之后新请求才生效。Cloud 网络故障会尝试上报，但不让问答因此失败。

边界：检查点保存完成的会话状态，**不是整条 RAG 链路断点续跑或历史时间旅行**。Langfuse 当前是问答追踪，不包含告警、业务仪表盘和完整监控平台。

## 阶段④：图片与扫描 PDF OCR

**功能：** 可点击原上传区域选择图片，也可拖拽；保留原有界面。普通 PDF 优先抽原生文本，扫描页先渲染再识别，切片保留物理页码并显示在引用卡片。支持 PNG/JPG/JPEG/WebP/BMP 单帧图片与未加密 PDF。

样本绝对目录：`D:\Projects\python-ai\data\samples\ocr`。不会自动把样本全部放入知识库，需要手动选择：

| 文件 | 内容 | 验收重点 |
| --- | --- | --- |
| `crane-scan.png` | 中文文字与英文验收码的清晰图片 | 图片识别，引用第 1 页 |
| `crane-scanned.pdf` | 一页纯图片 PDF | 扫描页识别，引用第 1 页 |
| `crane-mixed.pdf` | 第 1 页原生文字端口 29012；第 2 页扫描图端口 18743 | 原生文字与扫描页并存，扫描引用第 2 页 |

1. 选择 `crane-mixed.pdf` 上传，预期 2 个片段。若提示已存在，使用已有文档，不必删除重传。
2. 新建知识库会话，问：`CRANE-18743 对应的图像服务端口是多少？`
3. 答案应含 **18743**，右侧来源应为 **crane-mixed.pdf · 第 2 页**；展开片段检查英文验收码。
4. 再问：`CRANE-18743 资料中的请求失败退避时间是多少秒？` 查看原文 **9 秒**。
5. 仅删除本次临时资料，点“新会话”后问 `CRANE-18743`，来源应不再含已删除文档。若另外上传过同内容 PNG/扫描 PDF，它们仍可命中，因此逐个体验或查看具体文档 ID。

**为什么可能出现 3 个相似引用？** 三份 OCR 样本共用同一张测试图：PNG 的第 1 页、扫描 PDF 的第 1 页、混合 PDF 的第 2 页都有端口 18743、退避 9 秒及 CRANE-18743。全部上传后，三个文件的片段都可能被召回，来源对应三个文档，并非同一个片段被凭空复制三次。入库按文件原始字节指纹去重，不会把不同格式的同内容文件自动合并；融合检索只对同一文档/片段去重，目前未做跨文档近似内容合并。三条引用也不代表三个独立来源互相验证。要单独验收混合 PDF，只上传它，或在确认另外两份是可删除测试文件后手动删除它们，新建会话再测。

测试图中服务名称原文只有“苍鹭”，不是多个服务。若答案将 OCR 错字解释成不同服务名称，应对照原图纠正：图片与 PDF 的压缩/渲染可能使识别文字不同，不能把这些差异当作真实业务差异。端口和验收码应分别核对。

本次浏览器实测：上传混合 PDF → 回答 18743 → 引用第 2 页 → 删除 → 新会话固定拒答，完整通过。中文“苍鹭”在实际 OCR 中存在识别偏差，不能依赖名称逐字准确；财务金额、编号、法律等关键文本应与原件核对。复杂表格、手写、倾斜模糊图片未验证；大量原生文字与图片文字同在一页时，不保证图片区域都会触发 OCR。

限制默认每文件 30 页、每页 2000 万像素、每页 OCR 20 秒、全文件 OCR 时间预算 60 秒，上传上限仍为 20 MiB。超过限制应拆成有效小文件或降低图片分辨率后重试；不要只改扩展名。OCR 本地执行不产生识别 API 费用，但后续 embedding/问答仍收费。旧文档没有页码时显示原有引用形式，不伪造页码。

## 自动化验收：命令、输出与修复

在 **另一个 PowerShell 窗口**输入以下命令，服务日志终端不要输入测试命令：

```powershell
Set-Location 'D:\Projects\python-ai'
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check src tests scripts evaluation alembic training/train_classifier.py
.\.venv\Scripts\python.exe -m ruff format --check src tests scripts evaluation alembic training/train_classifier.py
node --test tests/frontend_sse.test.mjs
```

第一条默认离线：看到 `passed` 为通过，服务/OCR 实测默认 skipped。Ruff 应分别显示 `All checks passed!` 和 `... files already formatted`。Node 输出 pass、fail 0。若找不到 node，确认本机 Node 安装及 PATH；不要把它误认为 Python 功能失败。

下面两项标志开启真实 PostgreSQL/Qdrant/Redis 和 Tesseract 验收；模型使用替身，不调用付费模型，不要求 Web 服务启动。迁移测试需要本地数据库账号可创建临时数据库，测试会清理自己的随机库、集合与文档：

```powershell
$env:RUN_SERVICE_TESTS = '1'
$env:RUN_OCR_TESTS = '1'
.\.venv\Scripts\python.exe -m pytest
Remove-Item Env:RUN_SERVICE_TESTS
Remove-Item Env:RUN_OCR_TESTS
```

若失败，先保留错误，再按下面对应处理；不要删除测试以换取绿色结果。

| 现象 | 在哪里查及如何修复 | 复查 |
| --- | --- | --- |
| Ruff `would be reformatted` | 在 PowerShell 执行同范围 ` .\.venv\Scripts\python.exe -m ruff format src tests scripts evaluation alembic training/train_classifier.py`，它会改写列出的 Python 文件；与上传的 PDF 无关 | 重新运行 format --check、ruff check、pytest |
| Ruff 规则报错 | 输出的路径:行号及规则编号是位置，在编辑器打开该行。可先执行 `ruff check --fix` 的同范围命令修复可自动处理项，剩余按规则修改；不要盲目加 noqa | 同上；详细示例见故障排查.md |
| pytest FAILED | 记录第一条失败的 `文件::测试名` 和 traceback；运行 `python -m pytest 'tests/某文件.py::具体测试名' -vv`（python 换本项目解释器绝对/相对路径）缩小问题 | 修复后运行单项，再完整回归 |
| 迁移版本不匹配、启动失败 | 先备份，运行 scripts/migrate_db.py；用 alembic current/check 查版本及模型差异，保留日志 | head 正确、check 无差异、服务启动成功 |
| 会话未保存 | 看回答下方保存状态；检查 PostgreSQL/磁盘/权限和 `.demo-run/stderr.log`，核对 MEMORY_BACKEND、TTL、编号与模式 | 同会话两轮，再重启验证；新会话与过期历史不要求恢复 |
| Langfuse 401/403 | 本机编辑 .env，核对同项目 Public/Secret Key 与区域 LANGFUSE_HOST，保存后重启；不要发送密钥 | 发一次问题，在该项目查看新 trace |
| Langfuse 延迟、429/网络失败 | 等待后台上报，检查该区域网络和 Cloud 用量；历史 REST trace 接口可能 429，使用 Cloud UI 或 v2 observations 查询。仅填写了密钥不等于接收成功 | 以 Cloud 中新 trace 为准，问答仍应可用 |
| 分类 unavailable | 看 CLASSIFIER_MODEL_PATH 对应 JSON 是否存在，恢复版本管理的模型或按训练 README 重训；缺训练包则 `uv sync --project training --locked --python 3.12` | classify 接口恢复；低置信度与误分类应补真实标注数据重新评估 |
| OCR 未找到引擎/语言无法加载 | 用环境检查脚本确认路径与语言。自定义安装设置 TESSERACT_PATH；确认 OCR_TESSDATA_DIR 中有 chi_sim.traineddata、eng.traineddata，并重启 | 环境检查两种语言齐全，小图片上传成功 |
| OCR 超时/页数/像素超限 | 文件导出为清晰正向单帧图片，按页拆 PDF 或降低分辨率。仅在确认资源足够后调整对应 .env 上限并重启 | 先试随附样本，再试原文件；比较识别文字与原件 |
| OCR 识别错字 | 看引用片段与原图，改善扫描质量；对关键资料可人工校对后存 UTF-8 文本上传。OCR 不保证逐字准确 | 用真实问题核对事实和引用，而非只看上传成功 |

无法定位时，提供：输入位置、完整命令/网页步骤、预期与实际、失败文件和行号、时间对应的脱敏日志、环境检查结果及已尝试操作。不要发 `.env`、密钥或私有正文。
